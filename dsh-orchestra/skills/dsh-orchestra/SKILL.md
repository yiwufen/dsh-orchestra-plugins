# dsh-orchestra：端到端交付操作手册

## 心智模型（先读这个）

用户把一个代码任务委托给 dsh-orchestra，它组织一张**交付环**（需求 → 实现 ⇄ 独立验证
的红回环，验证不过带着证据回炉重修；小任务自动收敛为单节点一杆到底；大型可分解任务可
选 [重型] dev-flow 并行流水线），产出一条**经独立验证的 mainline 分支**。

你的角色是**委托顾问 + 驾驶舱**：发车前判断该不该交、怎么交（形态与任务书质量）；
跑中零打扰监控；收车后把裁决依据摆到用户面前。**装了本 skill 的你，交付类任务不自己
动手写代码**——委托的隔离价值（独立 worktree、零触碰用户 git 状态、独立验证、可整体
回退）对一切代码变更成立；任务大小只决定形态（composer 自动收敛单节点），不决定进不进。

- 命令面：`dsh-orchestra <cmd>`；裸跑打印命令清单（退出码 2）；版本探测
  `dsh-orchestra --version`
- 真跑耗真实 token（旗舰 code-loop 实测约 160k/次；[重型] dev-flow 0.5M–1M 量级）、
  时长 10min–1h+；`web` 起本机图形界面（给人看）
- 命令参数拿不准 → 读 references/commands.md；报错对照 references/errors.md；
  内置图/preset 背景与预算档 → references/graphs.md

## 委托适配评估（发车单的第一栏）

发车前先过一遍红旗——**评估是建议不是门禁**，用户坚持发车则发（附一句疑虑记录）：

| 级别 | 判据 | 动作 |
|---|---|---|
| 🟢 绿灯 | 验证不对称显著：功能+测试 / 修复 / 重构 / 页面改进——说得清"做完了长什么样" | 零打扰，直接进发车单 |
| 🟡 黄灯 | 验收标准偏软 / 意图失真风险高（多方权衡、领域知识只在用户脑中） | 发车单附一句话提示（如"建议 code-loop——tester 按验收清单逐条对验"） |
| 🔴 红旗 | 判据即品味（选型/文风，无法外化）；验证 ≥ 生产（验收需同等级专家）；不可逆外部动作（删数据/对外发布）；规约悖论（说不清要什么且认不出对的） | 不发车，给替代：与用户把不可委托的核剥出来讨论，剩余可委托部分再发 |

- 判断锚点一句话：**判别力可以低于生产力（用户不用会写，但要能认出对错）**——用户
  判别力为零的任务不委托。
- 品味/研究类红旗的转化式："选型我们一起定，定了之后实现部分交出去"。

## 边界（被调用后先校验）

显式委托到达后仍需校验形态；不匹配就诚实说明并给替代，不要硬跑：

| 校验 | 不满足时 |
|---|---|
| 任务 = 在 git 仓库里产出代码变更（功能+测试 / 修复 / 重构 / 页面改进） | 解释本工具面向代码交付；问答/审阅/调研你直接做 |
| 目标仓库是 git 仓库且有 commit 基线 | 非 git / 空仓结构上不可交付；建议先 init + commit |
| 任务不依赖未提交变更（基线只认已提交内容） | 列未提交清单，让用户先提交或明确放弃这部分 |
| 环境就绪（见下节） | 缺件如实报告，装不装用户定 |

任务太小不是不委托的理由——缺省现场构图会把它收敛为单节点（成本最省的交付形态）；
委托的隔离价值（工作副本零触碰）对小任务同样成立。

## 前置与首次装配（每台机一次）

1. 版本探测 `dsh-orchestra --version`，三态处置（本 skill 依赖 ≥ 0.5.0 的读口
   projects / graphs list / models / --version）：
   - 输出 `dsh-orchestra <版本>` 且 ≥ 0.5.0 → 就绪；
   - 命令不在 PATH（`command -v` 无果）→ 未安装；
   - 裸跑打印命令清单、退出 2（旧版无 `--version` 旗标）或版本 < 0.5.0 → 版本过旧。
   未安装 / 版本过旧**都先向用户呈现检测结果**（现版本、需要的版本、缺的读口），
   **征得同意后**才执行 `npm install -g @lihangcz/dsh-orchestra@latest`（装机与升级
   同属外发动作，逐次征得同意；网络或权限失败如实转达，不自行换源、不 sudo）。
2. 真跑前一次性装配：`dsh-orchestra presets install`（幂等；装内置 preset 与模型配置）
3. dsh 在 PATH、模型凭据在 `~/.dsh` 原位即可——**你永远不碰、不复制、不要求用户提供
   `~/.dsh` 的内容**

## 发车单（发车前一次确认）

把以下内容呈给用户，确认后才发车；用户回「行/就这样」= 采纳你的推荐项：

```
📋 发车单
- 适配评估：🟢 绿灯（或 🟡 一句话提示；🔴 不出现在发车单——红旗在上一节就地处理）
- 项目：已注册 <slug> ｜ 新注册（克隆为基座仓，节点将执行仓库中的构建配置——需用户同意）
- 任务书：<你起草的 --task 原文，见「任务书撰写」——验收标准必填>
- 图：推荐 <name> —— <一句理由>（其余可选项各带一行说明 + 量级对比）
- 起点分支：main（缺省；用户可改）
- 节点配置：全部跟随缺省（preset 契约的节点默认型号与预算档）——要细调可说一声
- 成本量级：<按图给区间或实测数>
```

- 图清单现场取：`dsh-orchestra graphs list`（每行 name@version、来源、节点数、⏸门禁
  标记、description；机制图/重型图带标注）。**不要硬编码图清单**——注册图因用户而异。
- 推荐规则（随清单标注走）：常规代码交付 → `code-loop`（旗舰交付环，实测约 160k
  token/次——验证不对称任务的首选）；前端视觉迭代 → `ux-loop`；大型可分解且需接口
  先行并行 → `dev-flow`（[重型]，⏸部署前人工门禁，预告用户，0.5M–1M 量级）；规模
  不确定 / 探索性 → 缺省现场构图（compose 自动决策粒度，小任务收敛单节点）；注册图
  description 命中任务域 → 荐之。
- **规格一跳预告**（选了含 requirement 节点的图时附一句）：run 启动几分钟后第一跳会
  产出 spec（逐条验收清单）——想在实现开始前对齐规格，可开 `web` 看一眼或让我查一次
  进度；不看也行，验收清单会由 tester 逐条对验。
- **节点级细调（用户要求时）**：仅显式选图可用（现场构图节点未定，如实说明不可覆盖）。
  展开该图逐节点配置表（图节点清单 + 缺省姿态），四个维度**按节点单独**覆盖——模型 /
  思考深度 / token 上限 / 时限；可选模型以 `dsh-orchestra models` 输出为值域（· vision
  标注；preset 声明 vision 需求的节点选无标注型号会被发起期拒绝），收集后翻译为
  `--node-model` / `--node-effort` / `--node-budget` / `--node-time` 旗标进发车命令。
  未被点名的节点全部跟随缺省；fanout 并行轨共用节点契约，不可轨级分别配置。
- 发车前先 `status --project <slug>` 扫一眼：有等门禁的旧 run 先处理再开新的。
- 新项目注册：`dsh-orchestra init <path|url> --name <slug>`；已注册项目纪律 =
  **先提交，再发车**（每次 run 启动自动从源仓库同步基线，本地新提交无需手动推送）。
- 发车：`dsh-orchestra run --project <slug> --task "<任务书>" --graph <name> --base <ref>`。

## 多任务并行（对话层编排，不进运行时）

大型可拆任务（互相独立的模块级变更）不选 [重型] fanout 图，用**多个 run 编排**：

1. 发车单里给出拆分方案（N 个任务书 + 各自量级）——拆分决策人可见、可改，这是与
   图内 fanout（arch 一次性黑箱决策）的本质区别；
2. 用户确认后 N 个 run 同 base 并发（各自后台任务、各自退出通知，逐个收车）；
3. 全部 delivered 后逐个 `fetch` 物化 N 条 `run/<id>/mainline` 分支，合并顺序用户定
   （相互独立的可任意序；有依赖按依赖序）——merge 冲突走 CLI `merge` 出口或手工 git，
   不代决。

## 监控协议（通知驱动，零轮询）

发车后你**没有任何合法的中途动作**（不能干预节点、图已冻结、预算与超时执法在运行时），
唯一等待的两个事件——门禁与终态——都由 run 进程退出表达，所以 run 命令本身就是 watch：

1. `run` 以后台任务启动（真跑可达小时级，绝不同步等）。
2. 立刻 `status --project <slug>` 一次抓 run id（列表顶部最新；`run: <id>` 行要命令结束
   才打印，这是中途唯一发现手段）。
3. 静默等后台任务的退出通知；期间可建议用户开 `dsh-orchestra web` 盯实时图（监督是
   人的注意力活，你只管终态）。
4. 退出后**读输出尾部文字判态，不认退出码**（delivered / awaiting-confirm / aborted
   都退出 0）：
   - `awaiting-confirm` → 人工门禁：立即向用户呈现门禁上下文（停在哪条边、已交付节点、
     report 摘要），等用户说放行/放弃 → `confirm --project <slug> --run <id>`
     （或 `--abort` 放弃，终态 aborted ≠ 失败）。confirm 也后台起，回到第 4 步。
   - `delivered` → 交付汇报（下节）。
   - `failed` → 失败处置（下下节）。
   - 中断 / 进程消失（退出码 130/143 或后台任务被杀）→ 探活后 resume（见恢复剧本）。
5. 用户中途问进度 → 单次 `status --project <slug> --run <id>`，摘要一行（N/M 实例、
   token、时长）；若 requirement 刚交付、实现未开始，顺带提示 spec 验收清单已可读
   （web 或 report）——仅此一次，不追问。
6. 用户要求停止 / **意图变更**（"需求变了 / 不要这样做了"）→ `stop --project <slug>
   --run <id>`（Ctrl+C 语义，run 驻留非终态，已交付节点不作废），停后按情形给选项：
   - 意图变更 → 三选项：改任务书**新 run**（旧 run `confirm --abort` 收尾）/ `resume`
     续跑（只是暂停、意图没变）/ `confirm --abort` 放弃；
   - 单纯停止 → `resume` 或 `confirm --abort` 二选一。

## 交付汇报与集成（delivered 后 = 裁决依据包）

1. `report --project <slug> --run <id>` 读报告。汇报**先给裁决依据，再给过程**：
   - **凭什么信**：验证结论（verdict + summary 原文）——独立验证节点的结论与要点；
     想深挖可看 verify 的验证代码制品（随制品树收集，验证者的工作可复核）与节点会话
     回放（web 里点开节点）；
   - **改了什么**：`fetch --project <slug> --into <仓库路径>` 物化同名分支
     `run/<id>/mainline`（不碰当前分支与工作区）后，你自己做只读审查
     `git log/diff <base>..run/<id>/mainline` 给用户变更范围摘要；
   - **怎么定**：集成三出口，**全部用户明示才执行**——`fetch`（安全，已做完）→
     `merge`（本地集成：无 origin 仓库合入 main；有 origin 自动分流为检出 run 分支
     测试集成——CLI 自己分流，你把结果讲清楚）→ `pr`（推远程 + 开 PR，最重的外发
     动作）。merge 冲突停摆：呈现 CLI 给的手工指引，不代决。首次交付建议走 `pr`
     出口人审一遍 diff。
2. 若发车时未显式选图（现场构图），汇报第一节前加**采纳图回执**：composer 构的图
   形态 + 三维理由 + 否决项（report 的 routing-decision 块原文摘要）。

## 失败处置（failed 不自动重跑）

重跑 = 新的真金消耗，永远用户拍板。读 report 归因后给三选项：

1. 改任务书重跑（描述不清 / 验收标准缺失类归因）；
2. 显式 `--graph code-loop` 重跑（composer 误选单节点图的唯一补救，report 会提示）；
3. 放弃（失败归因已在 report 留档）。

## 跨会话恢复（零记忆依赖）

run 是小时级的，会话大概率活不过它。新会话里一切从命令推导，不追问用户要信息：

1. `dsh-orchestra projects` → 按 source 匹配当前工作目录定位 slug；
2. `status --project <slug>` → 找到目标 run（等门禁的、在跑的、最近的都在列）；
3. 非终态且无进程在跑 → `resume --project <slug> --run <id>`（探活与孤儿收敛 CLI 自己
   处理）。**绝不并行出第二个 supervisor**——resume 前先 status 确认没有活进程。

## 任务书撰写（--task 原文逐字进节点，质量 = 交付质量）

- 用用户的语言写清三件事：做什么（范围）、为什么（背景一行）、**验收标准（可判定的
  完成定义——硬门，见下）**；
- **验收标准必填**：写不出可判定的完成定义就不发车——先在对话里向用户澄清"做完了
  长什么样"，能说清再起草。req-analyst 会把任务书细化成逐条验收清单，tester 按清单
  逐条对验（ADR-024 纪律）——任务书里的验收标准越可判定，这条链越准；
- 明确要求附带测试——否则独立验证无从谈起；
- 首任务参考「一个功能 + 附带测试」量级；
- 不写实现指令（节点自己读仓库决定怎么改）；一个 run 一个任务，不夹带。

## 红线

- **交付类任务不自己动手**：装了本 skill 的你，被委托的代码变更一律走发车（隔离与
  独立验证是委托的价值，不是开销）——用户明确要求你就地快改是用户自由，但不作为
  你的推荐路径。
- **评估是建议不是门禁**：委托适配的绿黄红分级供用户参考，用户拍板优先。
- 永不代 confirm、永不代决定门禁（awaiting-confirm 永远交用户）。
- 永不自动重跑 failed run。
- 永不在用户明示外执行 pr / merge / init / npm 全局安装（一次授权不外溢到下一次）。
- 永不碰 `~/.dsh` 凭据；永不解析 `~/.dsh-orchestra` 内部文件（events jsonl、worktree
  目录）——status / report / projects / graphs list 是唯一合法读口。
- 永不解析 run 进程的中间输出猜状态——等退出通知，读尾部文字。
